## 요약
- Git의 목적과 초기 설정: Git은 코드의 과거 버전을 기록·추적하고 안전한 협업을 돕는 프로그램이며, 최초 사용 시 사용자 이름과 이메일 등의 기본 설정을 완료해야 합니다.

- 작업 흐름과 파일 상태: 파일은 작업공간 ➔ 스테이징 영역(git add) ➔ 로컬 저장소(git commit) ➔ 원격 저장소(git push) 순으로 상태가 변하며 유기적으로 관리됩니다.

- 올바른 커밋 규칙: 커밋 메시지는 기능 추가(feat), 버그 수정(fix) 등 정해진 태그를 사용해 의미 있는 단위로 잘게 나누어 자주 기록하는 것이 좋습니다.

- 보안 및 문제 해결(.gitignore): API 키나 비밀번호 같은 민감한 정보나 불필요한 라이브러리는 .gitignore에 등록하여 GitHub 업로드를 방지하고 보안을 유지해야 합니다

   **사용 이유**
  이 말은 윈도우(Windows) 컴퓨터를 쓰면서 개발을 배울 때, "명령어를 입력하는 프로그램으로 일반 윈도우 창(CMD/PowerShell) 대신 'Git Bash'라는 프로그램을 쓰면 훨씬 편리하고 에러가 안 난다"는 뜻입니다.

쉽게 풀어서 설명해 드릴게요.

(1) 윈도우와 맥/리눅스는 언어(명령어)가 다릅니다

전 세계 개발 환경이나 인터넷에 있는 대부분의 코딩 강의, 실무 문서들은 **맥(macOS)이나 리눅스(Linux) 환경을 기준**으로 작성되어 있습니다. 이 환경들을 '유닉스(Unix) 계열'이라고 부릅니다.

문제는 **윈도우와 맥/리눅스가 사용하는 명령어(언어)가 완전히 다르다**는 점입니다.

| 기능 | 맥 / 리눅스 (유닉스 명령어) | 윈도우 기본 (CMD 명령어) |
| --- | --- | --- |
| **현재 폴더의 파일 목록 보기** | `ls` | `dir` |
| **파일 삭제하기** | `rm` | `del` |
| **현재 내가 있는 폴더 위치 보기** | `pwd` | `cd` (옵션 없이 입력) |

그래서 윈도우 기본 프로그램인 CMD(명령 프롬프트)를 켜고 강의에서 나오는 대로 `ls`를 입력하면, 윈도우는 이 말을 알아듣지 못하고 **"알 수 없는 명령어"라며 에러**를 뿜어냅니다.

---

(2) 'Git Bash'는 윈도우 속 '맥/리눅스 번역기'입니다

앞서 Git을 설치할 때 윈도우 사용자는 'Git for Windows'라는 프로그램을 설치하게 됩니다. 이걸 설치하면 'Git Bash'라는 특수한 터미널 프로그램이 함께 설치되는데요.

이 Git Bash는 **윈도우 컴퓨터 안에서 맥이나 리눅스 명령어(`ls`, `rm`, `pwd` 등)를 그대로 알아듣고 실행해 주는 역할**을 합니다.

따라서 Git Bash를 사용하면:

* 강의나 실무 가이드에서 "여기에 `ls`를 치세요", "`rm`으로 지우세요"라고 할 때, **윈도우 명령어로 바꾸어 생각할 필요 없이 그냥 똑같이 따라 치면 작동**합니다.
* 환경 차이로 인한 자잘한 에러를 겪지 않아도 됩니다.

---

(3) "목록에 없으면 설치가 안 된 것입니다"의 의미

윈도우 시작 메뉴(검색창)에 'Git Bash'를 검색했을 때 프로그램이 나타나지 않는다면, 앞서 설명한 Git 설치(Git for Windows 설치)가 제대로 이루어지지 않았거나 건너뛰었다는 뜻입니다.

**결론적으로,** 윈도우 환경에서 코딩 공부를 하실 때는 윈도우 기본 CMD를 쓰지 마시고, **Git Bash를 켜서 명령어를 입력하는 것이 정신 건강과 학습 효율에 훨씬 좋습니다.**

## .git / git 4가지 파일
git init -> 숨김폴더 .git/ 생성 => git이 관리하는 저장소
ls -a : 숨김 폴더 .git 확인

**⚠️ 주의 ⚠️** 
.git 폴더는 **절대 수동으로 열어서 수정하거나 삭제하지 마세요.** 
삭제하면 지금까지 쌓은 모든 이력이 복구 불가능하게 사라지고, 그냥 일반 폴더로 돌아갑니다.

| 공간 | 정체 | 여기로 보내는 명령 |
| :--- | :--- | :--- |
| **① 작업공간**<br>`Working Directory` | 💻 내가 실제로 파일을 만들고 고치는 폴더<br>(VS Code 등 에디터에 보이는 파일들의 편집 상태) | *(현재 작업 중인 공간)* |
| **② 스테이징**<br>`Staging Area` | 🎭 이번 커밋(버전)에 넣을 파일들만 골라 담는 **"대기 무대"** | `git add` |
| **③ 로컬 저장소**<br>`Local Repository` | 💾 내 컴퓨터에 커밋(스냅샷)이 쌓이는 곳<br>(`.git` 폴더 / 인터넷 연결 없이도 동작) | `git commit` |
| **④ 원격 저장소**<br>`Remote Repository` | 🌐 인터넷 서버에 있는 저장소<br>(GitHub / 백업·공유·협업을 위한 공간) | `git push` |

| 명령어 / 상황 | 파일 상태 | `git status` 메시지 의미 |
| :--- | :--- | :--- |
| `$ echo "hello" > note.txt` | 🟥 **Untracked** | `Untracked files:`<br>Git이 추적한 적 없는 새로운 파일이 작업공간에 생김 |
| `$ git add note.txt` | 🟩 **Staged** | `Changes to be committed:`<br>파일이 스테이징(무대)에 올라가 커밋 대기 중 |
| `$ git commit -m "docs: note 추가"` | ⬜ **Committed** | `nothing to commit, working tree clean`<br>로컬 저장소에 스냅샷 저장이 완료되어 정리된 상태 |

| 개념 항목 | 핵심 요약 |
| :--- | :--- |
| **🧭 나침반, `git status`** | 파일이 어느 공간(상태)에 있는지 헷갈릴 때마다 확인하는 필수 명령어입니다. 파일은 작업 흐름에 따라 `Untracked ➔ Staged ➔ Committed` 순으로 상태가 변합니다. |
| **🎭 왜 스테이징(add) 단계가 따로 있을까?** | 작업공간에서 바로 커밋하지 않고 **"이번 버전에 넣을 것만 고르는 단계"**가 필요하기 때문입니다. |
| **💡 고르는 단계의 가치 (이유)** | 10개의 파일을 고쳤더라도 **서로 관련된 3개의 파일만 묶어서 하나의 의미 있는 버전**으로 깔끔하게 만들고, 나머지는 다음 커밋으로 미룰 수 있는 자유를 줍니다. |

| 상태 (State) | 뜻 (의미) | VS Code 기호 | 다음 행동 |
| :--- | :--- | :---: | :--- |
| **Untracked** | Git이 아직 추적하지 않은 새 파일 | `U` | `git add` |
| **Modified** | 기존에 추적 중이던 파일이 수정됨 | `M` | `git add` |
| **Staged** | `add`가 완료되어 커밋을 기다리는 상태 | `A` 또는 `M` | `git commit` |
| **Committed** | `commit`이 완료되어 스냅샷 저장 성공 | *(표시 없음)* | 🎉 (완료) |

| 명령어 | 상태 이동 공식 | 역할 요약 |
| :--- | :--- | :--- |
| **`git add`** | `Untracked` / `Modified` ➔ **`Staged`** | 수정되었거나 새로 만든 파일을 **커밋 대기 무대**로 올립니다. |
| **`git commit`** | `Staged` ➔ **`Committed`** | 대기 무대에 놓인 파일들을 **최종 스냅샷(버전)**으로 기록합니다. |


## 3. git - github flow (add-commit-push / pull)
### 1. git 명령어
| 명령어 | 주요 기능 | 실무 팁 & 주의사항 |
| :--- | :--- | :--- |
| **`git status`** | 🧭 (수시로) 현재 파일들의 상태를 확인하는 나침반 | 헷갈릴 때마다 치는 습관을 들이면 좋습니다. |
| **`git add .`** | 🎭 변경된 모든 파일을 스테이징(무대)에 올림 | 특정 파일만 올리려면 `git add 파일명`을 사용합니다. |
| **`git commit -m "..."`** | 📸 스테이징에 올라온 파일을 스냅샷(버전)으로 확정 | `git commit -am "메시지"`로 add+commit 한 방에 가능 (추적 중인 파일만) |
| **`git push`** | 🌐 로컬 저장소의 커밋들을 원격(GitHub)에 업로드 | 최초 1회 원격 주소 연결(`remote add origin ...`) 후에는 `git push`만 입력 |
| **`git log --oneline`** | 📜 커밋 이력을 한 줄로 간결하게 보기 | 터미널 창에서 종료하고 싶을 때는 키보드 `q`를 누릅니다. |

### 2. VSCode -> GitHub 연동 방법
| 소스 제어 창 액션 | 연동되는 터미널 명령어 | 상태 글자(기호) 의미 |
| :--- | :--- | :--- |
| **메시지 입력 + ✓ Commit 버튼** | `git commit -m "..."` | **`U`** : Untracked (새 파일) |
| **파일 옆 + (Stage) 버튼** | `git add 파일` | **`M`** : Modified (수정됨) |
| **파일 옆 − (Unstage) 버튼** | `git restore --staged 파일` | **`A`** : Added (스테이징됨) |
| **파일 옆 ↩ (Discard) 버튼** | `git restore 파일` (변경 취소) | **`D`** : Deleted (삭제됨) / **`C`** : Conflict (충돌) |
| **... 메뉴 ➔ Sync / Push / Pull** | `git push` / `git pull` | *💡 팁: 클릭 방식과 터미널 방식을 섞어 써도 무방함* |

### 3. Commit 
| 태그(Type) | 용도 및 의미 | ✗ 나쁜 예 (지양) | ✓ 좋은 예 (지향) |
| :--- | :--- | :--- | :--- |
| **`feat`** | 새로운 기능 추가 | "수정", "작업함" | `feat: 로그인 화면 추가` |
| **`fix`** | 버그/오류 수정 | "오류 고침", "ㅇ" | `fix: 로그인 버튼 클릭 오류 수정` |
| **`docs`** | 문서 수정 (README 등) | "리드미" | `docs: README 사용법 보강` |
| **`refactor`**| 코드 리팩토링 (기능 변경 無)| "코드 정리" | `refactor: 로그인 검증 로직 개선` |

💡 커밋 주기 팁: 하루 끝에 몰아서 한 번에 커밋하기보다, 기능 하나가 끝날 때마다 의미 단위로 잘게 나누어 자주 커밋하는 것이 나중에 되돌리거나 읽기 쉽습니다.

### 4. 로컬 <-> 원격 흐름
| 명령어 | 흐름 방향 | 핵심 정의 및 왜 쓰는가? |
| :--- | :--- | :--- |
| **`git add`** | 작업공간 ➔ 스테이징 영역 | **오른쪽으로 밀어 올리기 (1단계)**: 사진을 찍기 전, 이번 버전에 기록할 파일들만 골라 무대 위에 세워두는 단계입니다. |
| **`git commit`**| 스테이징 ➔ 로컬 저장소 | **오른쪽으로 밀어 올리기 (2단계)**: 무대 위의 파일들을 '사진(스냅샷)'으로 확정해 저장합니다. (여기까진 내 컴퓨터 안에서만 동작) |
| **`git push`** | 로컬 저장소 ➔ 원격(GitHub) | **오른쪽으로 밀어 올리기 (3단계)**: 내 컴퓨터에 쌓인 커밋들을 인터넷(GitHub) 서버로 업로드하여 백업하고 팀원과 공유합니다. |
| **`git pull`** | 원격(GitHub) ➔ 작업공간 | **왼쪽으로 당겨 내려받기 (역방향)**: 원격의 최신 변경 사항을 가져와(`fetch`) 내 파일에 합치는(`merge`) 작업을 한 번에 처리합니다. |
| **`git clone`** | 원격(GitHub) ➔ 로컬 통째로 | **최초 복제**: 새 컴퓨터에서 프로젝트를 처음 시작할 때, `git init` 대신 원격 저장소를 통째로 내 컴퓨터로 다운로드합니다. |

🔄 협업의 하루 루틴: git pull (원격 최신본 받기) ➔ 파일 작업 ➔ git add ➔ git commit ➔ git push (원격에 올려 마무리)


## .gitignore (나만보기 & 보안)
### 1. .gitignore 올리면 안되는 파일
| 분류 | 대상 예시 (무시할 항목) | 왜 제외해야 하는가? (기준) |
| :--- | :--- | :--- |
| **🔐 민감한 정보** | `.env`, `*.key` | API 키, DB 비밀번호, 토큰 등 유출 시 금전적·보안상 치명적인 사고로 이어짐 |
| **📦 라이브러리** | `node_modules/`, `.venv/` | 파일 수가 수천 개에 달해 저장소를 무겁게 만듬 (남이 clone 후 다시 설치하면 됨) |
| **⚙️ 부산물/결과물** | `.DS_Store`(맥), `Thumbs.db`(윈도우), `dist/`, `build/`, `__pycache__/` | OS나 편집기(VS Code)가 자동으로 생성하는 파일 및 빌드 결과물 (코드 본질이 아님) |

**🚨 [주의]** 
이미 커밋된 파일을 뒤늦게 .gitignore에 넣을 때 (가장 흔한 함정)

.gitignore는 아직 추적되지 않은 파일에만 적용됩니다. 이미 올라간 파일을 안전하게 빼려면 아래 순서대로 터미널에 입력해야 합니다.
git rm -r --cached .env         # 1. 파일은 놔두고 Git의 '추적'만 해제 (--cached가 핵심!)
echo ".env" >> .gitignore       # 2. .gitignore 파일 목록에 추가
git commit -m "chore: .env 추적 제외" # 3. 커밋하여 반영

**⚠️ 보안 경고**
이미 GitHub에 push된 비밀번호는 추적을 빼도 **과거 커밋 이력(History)**에 남아있습니다. 유출된 토큰이나 비밀번호는 **반드시 GitHub나 해당 서비스에서 즉시 재발급(무효화)**해야 안전합니다.

### 2. 명령 사전
| 상황 | 실행할 터미널 명령어 | 비고 / 팁 |
| :--- | :--- | :--- |
| **오늘 작업 시작할 때** | `git pull` | 원격의 최신 상태를 먼저 받고 시작하는 것이 기본입니다. |
| **뭐가 바뀌었는지 알고 싶을 때** | `git status` / `git diff` | `status`는 현재 상태의 나침반, `diff`는 구체적인 코드 비교 |
| **작업을 기록 / GitHub에 올릴 때**| `git add .` ➔ `git commit -m "..."` ➔ `git push` | 가장 기본적이고 자주 쓰는 3단계 리듬 |
| **파일 잘못 고침 (커밋 전 돌리기)**| `git restore 파일명` | 마지막 커밋 상태로 파일을 되돌립니다. |
| **add 잘못함 (스테이징 취소)** | `git restore --staged 파일명` | 파일 수정 내용은 유지하고, 무대에서만 내립니다. |
| **방금 한 커밋 메시지 오타 수정** | `git commit --amend` | 방금 올린 커밋의 메시지를 수정할 수 있습니다. |
| **방금 한 커밋 자체를 취소(무르기)**| `git reset --soft HEAD~1` | 커밋은 취소되지만, 내가 수정한 코드(변경분)는 그대로 유지됩니다. |
| **이미 push한 커밋 안전하게 취소**| `git revert <커밋ID>` | 취소했다는 새로운 커밋을 만들어 안전하게 역방향으로 되돌립니다. |
| **급히 브랜치 바꿈 (커밋 안 됨)** | `git stash` ➔ 복귀 후 `git stash pop` | 작업 중이던 코드를 임시 임시보관함(stash)에 치워두는 기능 |
| **새로운 기능 따로 작업할 때** | `git switch -c 브랜치명` | 새 브랜치를 생성함과 동시에 그 브랜치로 이동합니다. |
| **push 거부됨 (원격에 새 커밋 있음)**| `git pull` ➔ (충돌 해결 후) ➔ `git push` | 원격의 최신 본을 먼저 가져와 합친 뒤 push해야 합니다. |

### 3. 협업 가이드 (충돌 해결 & 브랜치 습관화)
| 주제 | 핵심 정의 및 해결 방법 | 실무 원칙 및 꿀팁 |
| :--- | :--- | :--- |
| **💥 충돌 (Conflict)** | 같은 줄을 나와 남이 다르게 고친 상태에서 합칠 때 발생합니다. | `<<<< HEAD`(내 내용)와 `>>>> main`(남의 내용) 사이에서 최종본을 사람이 직접 고른 뒤, `git add` & `git commit`으로 해결합니다. (VS Code 클릭 버튼 활용 가능) |
| **🌿 브랜치 습관** | 브랜치는 가벼운 포인터라 많이 만들어도 괜찮지만, **수명이 길어지면 충돌 지옥**이 됩니다. | 💡 **"짧게 살고 ➔ 자주 병합 ➔ 끝나면 삭제"**<br>기능 작업이 끝나면 GitHub에서 Pull Request(PR)를 거쳐 병합하고, `git branch -d 브랜치명`으로 삭제하세요. |



**🔄 전형적인 하루 흐름**
<TERMINAL> 
git pull                          # 1. 최신 상태로 맞추기 
git switch -c feature/login       # 2. 작업 브랜치 생성 
# ... 코드 작업 ... 
git status                        # 3. 뭐 바뀌었나 확인 
git add .                         # 4. 스테이징 
git commit -m "feat: 로그인 추가"  # 5. 커밋 
git push -u origin feature/login  # 6. 원격에 올리기 
# 7. GitHub에서 Pull Request 생성 → 리뷰 → merge
